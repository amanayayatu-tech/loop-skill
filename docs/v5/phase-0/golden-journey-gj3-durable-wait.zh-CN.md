# GJ-3：跨等待窗口的长程任务

## 最终意图

证明自然等待不是终止：LoopSkill 完成前段工作后持久退出占用，在约定时间由已验证的 Codex Host 能力重新进入同一业务身份，继续后段工作且不重复前段效果，最终交付业务结果。

## 固定任务

用户原话：

> 先生成并验证第一份本地交付物；等待合同中的 `not_before` 时间后，再基于第一份结果生成第二份交付物并做最终 readback。等待期间不要占用常驻进程，不要让我重发任务。只写这个临时项目，不联网、不发布、不提交。

旅程使用一次性真实 Git 工作区和私有数据根。第一份交付物具有固定 effect key 和内容摘要；第二份必须引用该摘要。等待由绝对时间和单调条件共同判定，不把短 observation timeout 当作到期。

## 时长层级

| 层级 | 等待窗口 | 允许主张 |
| --- | --- | --- |
| Phase 2 development spike | 2–5 分钟，主动进程在等待前退出 | 只证明本机机制和身份续接，不是多日能力 |
| Phase 3 regression | 跨至少一次独立 Host 唤醒，并注入一次进程终止 | 证明恢复行为，不是发布耐久证据 |
| Phase 4/5 release journey | 连续不少于 48 小时，跨两个自然日和至少两次 Host 重新进入 | 才可支持“多日级耐久等待”发布主张；操作系统关机恢复仍不在承诺内 |

## START 前必须闭合

1. Host 的 session/thread identity、resume 或 heartbeat 接口已用同等权限真实探测，最长窗口覆盖合同。
2. 唤醒调度已 readback，目标仍是同一业务身份；若只能创建新独立任务，拒绝 START。
3. 工作区、私有数据根、写范围、可执行命令和最终 verifier 在重新进入后仍可解析。
4. 第一段效果可用 effect key 与内容摘要确认；状态未知时禁止再次写入。
5. 明确系统睡眠/关机、凭据失效、工作区身份漂移和调度被用户删除的停止边界。

## 一次 START 后的路径

1. 工作段 A 创建、验证并持久化第一份交付物和 effect identity。
2. 写入最小等待事实：业务身份、`not_before`、第一份摘要、下一验收和已知效果；调度 durable wake 后 readback。
3. 主动进程退出；等待不显示为完成、失败或紧急停止。
4. 故障注入使首次运行进程/turn 终止；到期后 Host 重新进入同一身份。
5. 续接先 readback 第一份效果；已存在且摘要一致则绝不重写，未知则紧急停止而非盲重发。
6. 工作段 B 生成第二份交付物，运行最终 verifier，报告完整业务结果。

## 通过事实

- 用户只确认一次且无需重发任务；技术性人工介入 `0`。
- 等待期间没有常驻 Worker/Controller/daemon 进程。
- 同一业务身份、同一工作区和同一效果事实跨唤醒保持；第一份效果写入次数恰为 `1`。
- 续接后第二份交付物引用第一份 exact digest，最终 readback 与报告一致。
- 48 小时发布运行的开始、唤醒、续接、结束时间来自机器证据；短时 spike 不能冒充。
- 调度或身份不可验证时在 START 前阻断；START 后发生未预见漂移时准确紧急停止且不计成功。
